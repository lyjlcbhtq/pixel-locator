# Benchmarks

两个可自行运行的基准脚本。**README 里的每一个数字，都可以在这里复现。**

```bash
python benchmarks/bench_ocr.py       # OCR 速度：冷启 / 热调用 / 缓存 / 区域 / 降采样
python benchmarks/bench_tmatch.py    # 模板匹配：全屏 vs 锚点窗口
```

两个脚本都需要**真实屏幕**（用 `mss` 截屏）。没有桌面环境时会给出提示并退出。

---

## 本机参考数据（2560×1440，纯 CPU，OpenCV 为 CPU 构建版）

### OCR（bench_ocr.py）

| 模式 | 耗时 | 说明 |
|---|---|---|
| 冷启（含引擎加载） | ~6047 ms | 引擎加载约占 3.8 s |
| 热调用（同进程，引擎已复用） | ~2280 ms | 全屏推理的真实成本 |
| `scale=0.5` | ~1695 ms | 块数 76 → 72（漏掉约 5%） |
| 区域 800×600 | ~1280 ms | **只剩 5 个文字块也要 1.28 s → 存在物理下限** |
| 子进程首次查询（真 OCR） | ~7082 ms | 进程启动 + 引擎加载 + 推理 |
| 子进程再次查询（内容缓存命中） | ~600 ms | 约 12 倍 |
| 守护进程 + 缓存命中 | **~175–225 ms** | 约 35 倍 |

**结论**：引擎加载与进程启动是大头；OCR 推理本身有约 1.2 s 的下限，
**靠调参无法到毫秒级**，所以毫秒级定位必须绕开 OCR。

### 模板匹配（bench_tmatch.py）

| 模式 | 耗时 | 说明 |
|---|---|---|
| 全屏 2560×1440 匹配 | ~147 ms | 多尺度搜索 |
| 锚点窗口 300×300 匹配 | **~4 ms** | 净提速约 **37 倍**，坐标完全一致 |

**结论**：先用便宜线索（已知区域 / OCR 锚点）缩小范围，再做模板匹配，
是达到毫秒级定位的关键路径。批量场景更能体现差距：
连续匹配 20 次 → 全屏约 2.9 s vs 窗口约 0.08 s。

---

## 读数字时请注意

1. **绝对耗时有机器差异**（CPU 型号、屏幕分辨率、文字数量都会影响），重点看**相对倍数**
2. **块数**是召回率指标：降采样或缩小区域换来速度时，要看漏掉了多少文字
3. `--no-cache` 才是真实的 OCR 耗时；带缓存的数据反映的是重复查询同一画面的情况
4. 本项目的 `tmatch` 在有 CUDA 的机器上会自动加速，无卡自动降级 CPU，**结果一致**
